BidFit · LaunchRadar

입찰 공고 검토와 출시 전 선행조사를 돕는 AI 스킬 두 개입니다. 결과마다 근거를 붙이고, 아직 확인 안 된 조건은 따로 보여 줍니다.

문제
입찰 공고 검토와 출시 전 선행조사는 확인에 시간이 많이 들고, 일반 AI 요약은 확인 안 된 내용까지 단정해 버립니다.
해결
BidFit은 공고를 Go / Review / No-go로, LaunchRadar는 제품 아이디어를 확인 우선 / 추가 검증 / 초기 검증 통과로 나누고 근거 링크를 붙입니다.
내 역할
두 스킬의 문제 정의, 워크플로, 판정 규칙 설계와 제출 자료 정리

출력 구조를 설명하기 위한 예시 화면입니다.

01 · 배경

매일 반복되는 두 가지 확인 업무

  • 중소기업의 제안·영업 담당자는 매일 나라장터 공고를 검색하고, 원문·첨부를 회사의 면허·인증·실적과 대조합니다. 지역·면허·직접생산·공동수급·마감 조건을 확인하느라 공고마다 수십 분이 들고, 하나를 놓치면 잘못된 참여 판단으로 이어집니다.
  • 창업자는 출시 전에 제품명과 아이디어를 상표·특허·논문 검색창에 따로 넣어 보고, 흩어진 결과를 스스로 하나의 판단으로 묶어야 합니다.

02 · 문제 정의

AI 요약이 틀린 확신을 주는 경우

회사 정보도 없는데 "참여 가능"이라고 하거나, 검색 결과가 안 나왔다는 이유로 "써도 되는 이름"이라고 하면 사용자는 결국 원문을 처음부터 다시 봐야 합니다.

그래서 두 스킬 모두 사람이 직접 판단해야 하는 부분을 분명하게 표시하는 걸 가장 먼저 챙겼습니다.

03 · 해결 방안 ①

BidFit: 공고를 Go / Review / No-go로 나누기

회사 프로필·관심 분야 검증
조건 완화 없이 마감 전 후보 공고 검색
공고별 충족·불충족·미확인·blocker 분리, 원문·첨부 확인
비교표·근거 URL·다음 행동·제안서 초안, 매일 08:00 최대 3건 브리핑
  • 참여를 막는 조건이 하나라도 있으면 No-go, 필수 조건을 확인할 수 없으면 Review, 근거가 충분할 때만 Go로 분류합니다.
  • 모르는 회사 정보는 짐작해서 채우지 않고 [회사 입력 필요]로 남깁니다. 적합도 점수를 참가 가능 확률처럼 보이게 쓰지도 않습니다.
  • 날짜, 금액, 공고번호는 원문과 한 번 더 맞춰 봅니다. 맞는 공고가 없으면 0건이라고 알리고, 데이터 오류가 나면 한 번만 다시 시도한 뒤 멈춥니다.

데이터는 자체 운영하는 공개 읽기 전용 kr-bid MCP와 조달청 나라장터 입찰공고정보만 씁니다.

04 · 해결 방안 ②

LaunchRadar: 상표·특허·논문을 한 번에 보고 출시 판단하기

제품명·문제·기술어로 검색 지도 작성
KIPRIS 상표·특허 조회
OpenAlex에 색인된 arXiv 연구 조회
근거 ID를 붙여 판정·차별화 지도·14일 계획 작성
  • 판정은 확인 우선, 추가 검증, 초기 검증 통과 세 가지입니다. 더 신중한 판정에 해당하는 조건이 하나라도 있으면 그쪽으로 판정합니다.
  • 충돌 가능성이나 차별화 방향을 적을 때는 상표(TM), 특허(PT), 논문(RX) 근거 ID를 꼭 하나 이상 붙입니다. 근거 없이 추론한 내용은 '가설'로 표시하고 어떻게 확인할지 같이 적습니다.
  • 검색 결과가 없다고 해서 '사용 가능', '침해 없음', '등록 가능'이라고 쓰지 않습니다. 주요 검색이 실패했을 때도 '초기 검증 통과'는 주지 않습니다.
  • 법률 의견이나 침해 판단은 하지 않고, 전문가에게 확인받아야 할 부분을 따로 표시합니다.

05 · 내 역할

문제 정의부터 제출까지 맡았습니다

  • 두 스킬의 문제 정의, 워크플로, 데이터 출처, 재현 방법을 제출 양식에 맞게 통합
  • 미확인 조건 표시, 실패 시 중단, 판정 우선순위 같은 안전 규칙과 테스트 시나리오 정리
  • 스토어 등록명·태그·첨부 파일·API 키 같은 민감 정보 취급을 체크리스트로 관리

두 스킬 모두 Upstage Solar Pro4만 쓰고 외부 LLM API는 쓰지 않았습니다.

06 · 회고

할 일보다 하지 말 일을 더 많이 정했습니다

배운 점

  • 두 스킬의 설명서를 다시 보면 해야 할 일보다 하지 말아야 할 일이 더 많습니다.
  • 검색 조건을 임의로 넓히지 않기, 결과가 없으면 0건이라고 쓰기, 오류가 나면 한 번만 다시 시도하고 멈추기, 검색 결과가 없다고 "사용 가능"이라고 쓰지 않기.
  • 입찰이나 상표처럼 한 번 틀리면 비용이 큰 업무에서는 이런 제한이 있어야 결과를 믿고 쓸 수 있다고 봤습니다.

아쉬운 점과 다음 단계

  • 제한이 많을수록 Review나 '추가 검증'으로 넘어가는 항목도 늘어납니다. 사람이 확인할 일이 너무 많으면 도구를 쓰는 의미가 줄어듭니다.
  • 다음에는 실제 입찰 담당자와 창업자에게 써 보게 하고, 이 항목들을 확인하는 데 시간이 얼마나 드는지부터 재 보고 싶습니다.
